# Maybox 다음 작업 선정

긴급도·중요도로 기본 순서를 잡고, 비슷한 우선순위에서는 사람의 개입이 적고 구현·검증·리뷰까지 끝낼 준비가 된 일을 앞세운다. 이슈를 새 세션에서 책임지고 마칠 작업 단위로 묶고, 사용자가 한눈에 다음 묶음을 선택할 수 있도록 한국어로 보고한다.

## 근거와 현재 작업

첫 조회 전에 [공통 연결·탐색 범위](../maybox-board-sync/references/sources.md)를 읽는다. 해당 런타임의 Linear·Slack·GitHub 연결을 사용한다.

- Maybox 활성 이슈를 페이지 끝까지 읽고, 추천 후보의 전체 본문·관계·관련 댓글과 현재 PR을 확인한다. 관련 기존 세션·작업 원장이 있으면 실제 상태를 대조해 새 위임과 기존 작업 이어가기를 구분한다.
- 같은 대화에서 보드를 최신화했다면 조사 근거를 재사용하고, 그 뒤 바뀔 수 있는 이슈·PR·작업 상태만 추가 확인한다. 긴급도·완료 조건·책임이 불명확한 후보에 한해 관련 Slack 합의·코드로 범위를 좁혀 확인한다.
- 보드 최신화가 필요하면 이유를 설명하고 `maybox-board-sync`로 연결을 제안한다. 사용자가 두 작업을 함께 요청했다면 최신화 후 바로 선정으로 이어간다. 접근할 수 없는 근거는 미확인으로 남긴다.
- 완료 근거가 있는 이슈는 상태 재확인 대상으로, 진행 중인 세션·PR이 있는 이슈는 이어가기 대상으로 보고한다. 새 구현 묶음으로 중복 추천하지 않는다.

기본 결과는 읽기 전용 추천이다. 이 스킬 호출만으로 Linear 상태·우선순위·담당을 변경하거나 새 세션을 생성하지 않는다.

## 우선순위 판단

1. **미룰 때 생기는 손실:** 현재 업무 중단, 재고·수량 정합성 위험, 반복 오류, 확정 일정, 중요한 후속 작업의 차단을 먼저 본다. 외부 대응만 필요한 긴급 장애도 보고 맨 앞에 두고 필요한 대응을 적는다.
2. **현장 효과와 선행 효과:** 발생 빈도, 작업자 부담, 영향을 받는 흐름, 다른 작업을 열어주는 효과를 본다. Linear 중요도는 출발점이며 최근 근거와 추천 순서가 다르면 이유를 적는다.
3. **완료 준비도:** 비슷한 중요도에서는 요구·완료 기준·검증 방법이 명확하고 외부 의존이 적은 일을 앞세운다. 코딩이 짧아도 현장 장비·화면 승인·외부 담당자 때문에 검증이나 마무리가 멈추면 그 조건을 표시한다.
4. **사람의 판단 부담:** 좁은 선택과 추천안이 준비돼 있어 가벼운 결정으로 구현 범위를 고정할 수 있는 작업도 빠른 후보에 포함한다. 업무 정책·책임·예외 처리가 불명확하면 조사·설계 대상으로 둔다.

확인되지 않은 영향·기간을 숫자로 만들어 점수화하지 않는다. 중요한 설계 과제를 쉬운 개선 뒤로 계속 밀지 말고, 구현 묶음과 독립적인 조사·결정 묶음을 함께 추천할 수 있는지 본다. 코드로 조사 가능한 내용은 조사 작업으로 맡기고, 업무 정책·선호처럼 사람이 정할 내용만 질문으로 남긴다.

| 시작 방식 | 조건 | 다음 행동 |
| --- | --- | --- |
| 바로 위임 | 요구·완료 기준·검증 방법과 실행 조건이 준비됨 | 구현·검증·리뷰까지 맡기기 |
| 짧은 논의 후 위임 | 좁은 선택과 추천안이 있으며 답변 후 범위가 고정됨 | 결정할 내용을 먼저 확인하기 |
| 조사·설계부터 | 운영 사실·정책·시스템 경계의 불확실성이 큼 | 조사·설계 산출물을 맡기기 |
| 외부 조건 대기 | 외부 담당자·현장 접근·선행 작업이 필요함 | 필요한 조건과 다시 시작할 계기를 적기 |

## 세션 단위로 묶기

한 묶음은 한 세션에서 책임질 수 있는 결과와 완료 기준을 가진다. 같은 사용자 흐름·도메인·담당 범위, 조사·검증의 공통점, 실제 의존성으로 묶는다. 같은 파일·화면 검사를 공유하는 작은 작업은 합치고, 긴 설계·외부 대기가 독립적인 구현을 막으면 분리한다. 관련성이 약한 일을 한 묶음으로 몰지 않는다.

각 묶음에는 포함 이슈·구현 범위 또는 조사 산출물·완료 기준·남은 결정·선행 조건을 남긴다. 원래 이슈의 미합의 범위를 구현 확정 사항으로 바꾸지 않는다.

병렬 가능 여부는 공통 파일·API·마이그레이션·테스트 환경·기기와 업무 결정을 기준으로 판정한다. 독립 구현은 병렬, 공용 변경의 통합은 순차처럼 조건을 명시한다. 사람이 동시에 검토할 묶음과 결정을 감당할 수 있는 조합을 추천한다.

## 사람 개입 표시

**정도·구체적인 행동·시점·그 뒤 맡길 수 있는 범위**를 묶음별로 적는다. 개입 요구는 사용자 합의·완료 조건·현재 작업 규칙에서 확인하며, 시작 방식과 별개로 구현 이후 화면 확인·현장 검증이 필요한지도 포함한다. 확인된 필수 개입과 제안하는 검토는 구분한다. 이미 승인된 설계·위임·리뷰·머지 권한은 유효 범위에서 재사용하고, 모든 작업에 사람의 코드 리뷰를 일률적으로 추가하지 않는다.

| 개입 정도 | 보고할 내용 |
| --- | --- |
| 거의 없음 | 묶음 선택 외 추가 큰 결정 없음. 실제로 필요한 마무리 확인이 있으면 별도로 적기 |
| 가벼움 | 준비된 안 중 선택, 문구·배치 확인 등. 무엇을 몇 번 결정·확인할지 적기 |
| 큼 | 정책·책임·예외 시나리오 합의나 반복 설계 논의. 남은 핵심 결정 적기 |
| 외부 대응 | 담당자 연락·현장 테스트·기기 연결 등. 사용자에게 필요한 행동과 외부 의존 구분하기 |

화면 승인이 완료 조건인 경우의 예: `가벼움 · 착수 전 메뉴 위치 1개 선택, 구현 후 실제 화면 확인 → 선택한 범위의 구현·검증·리뷰를 위임`. 확정되지 않은 회수·소요 시간은 추정 또는 미확인으로 표시한다. 정책이 미조사 상태면 단순한 예/아니오 승인으로 축소하지 않는다.

## 최종 보고

확인 기준일과 핵심 추천을 한두 문장으로 먼저 적고, 사용자가 고를 상위 묶음을 보통 3~5개로 압축한다. 전체 후보 분석은 뒤에 풀어놓지 말고 요청 시 보여줄 근거로 남긴다.

| 추천 | 작업 묶음·이슈 링크 | 지금 할 이유 | 시작 방식 | 사람 개입·그 뒤 진행 범위 | 병렬·선행 관계 |
| --- | --- | --- | --- | --- | --- |
| 1 | 묶음 이름 · 이슈 링크 | 확인된 손실·효과 | 바로 위임 등 | 정도 · 행동과 시점 → 위임 가능한 범위 | 함께 진행할 묶음 또는 먼저 필요한 작업 |

이어서 **추천 조합** 한 문장, **기존 작업 이어가기·보류·미확인**의 핵심 이유를 짧게 적는다. 긴급 외부 대응은 개발 추천 목록에 묻히지 않게 먼저 드러낸다. 중요하지만 설계가 필요한 작업의 착수 제안도 함께 보여준다.

마지막에는 사용자가 묶음을 선택하도록 안내한다. 실제 위임을 요청하면 선택한 범위와 확인된 사람 결정·의존성을 전달하고, 별도로 세션 생성이 승인된 환경에서 `orchestrate`로 이어간다. 완료 기준이 설계 산출물인 세션과 제품 구현 세션을 구분한다.
