# 구현 워커가 도는 동안의 git 규칙

서브에이전트는 컨텍스트만 격리된다. **파일시스템, git 인덱스, stash 스택, refs 는 공유**다. worktree 를 나눠도 stash 와 refs 는 `.git` 공통 디렉터리에 하나뿐이다. 아래는 전부 실사고에서 나온 규칙이다.

## 조율자가 지킬 것

- **구현 워커가 도는 동안 `git add -A` / `git add -u` / `git commit -a` 를 쓰지 않는다.** 문서 한 줄을 커밋할 때도 경로를 명시해 스테이징한다. 컨트롤러의 `git add -A` 가 구현자가 쓰던 소스·테스트 82줄을 문서 커밋에 쓸어 담은 사고가 있다.
- **같은 브랜치의 커밋을 만지는 일(스테이징·커밋·amend·rebase)은 한 번에 한 에이전트만.** 두 워커에게 각자 커밋을 amend 시켰다가 한쪽이 상대 파일을 쓸어 담고 상대 메시지를 채택한 사고가 있다.
- **워커에게 `git stash` 를 시키지 않는다.** stash 는 저장소 전역 스택이라 무관한 브랜치의 stash 가 pop 되어 파일 5개에 conflict 를 낸 사고가 있다. 임시 대피는 파일 복사나 별도 커밋으로.
- 디스패치 전 `git rev-parse HEAD` 를 BASE 로 기록한다. 리뷰 diff 와 수정 라운드 diff 는 BASE 기준이다. `HEAD~1` 은 여러 커밋짜리 태스크의 앞 커밋을 조용히 버린다.

## 병렬 구현이 꼭 필요할 때

- 각 워커를 `isolation: "worktree"` 로 격리하거나, 서로 겹치지 않는 파일 집합만 맡기고 **커밋은 조율자가 순차로** 한다.
- worktree 는 순차로 만든다. `git worktree add` 를 동시에 실행하면 `.git/config.lock` 을 두고 경쟁해 한쪽이 실패하고 고아 브랜치가 남는다.
- 병렬 read·분석·리뷰는 변경이 없으므로 안전하다.

## 스테이징이 오염됐을 때

푸시 전이고 도는 구현자가 없는지 먼저 확인한다.

1. `git reset <base>` — **mixed** reset. `--soft` 는 인덱스를 그대로 두어 이어지는 `git add <일부>` 가 무의미해지고 다시 한 커밋에 전부 들어간다.
2. 경로별로 스테이징해 커밋을 다시 나눈다.
3. `git rev-parse HEAD^{tree}` 를 전후 비교해 내용이 보존됐음을 증명한다.
4. 테스트를 다시 돌린다.

## 사고 뒤 확인 순서

`git stash list`(항목이 남았나) → `git stash show --stat stash@{N}`(내용이 온전한가) → `git status`(원복됐나) → `git show --stat <커밋>`(남의 파일이 섞였나). stash 항목은 drop 하지 않고 보존한다.
