# Maybox 작업 세션 조율

선택된 작업 묶음을 사용자 소유의 새 세션에 맡긴다. 담당 세션은 문제 조사부터 구현·검증·PR·수정까지 책임지고, 조율자는 진행 감시·질문 판단·독립 리뷰·머지 순서를 책임진다. 구현 작업의 기본 목표는 승인된 범위의 실제 머지와 이슈 완료다. 설계 산출물만 요청한 작업은 그 산출물까지다.

이 스킬을 만드는 요청이나 다음 작업 추천만으로 실제 작업 세션을 만들지 않는다. 새 세션 생성·메시지·머지의 실제 사용자 승인 범위를 먼저 확인한다. 기존 승인은 유효 범위에서 재사용한다.

## 묶음과 시작 모드

`maybox-next-work`의 선택 결과를 받아 범위·완료 기준·사람 개입·선행 관계를 확인한다. 새로운 증거가 없으면 보드 전체를 다시 조사하지 않는다. 최초 연결에는 [Maybox 공통 좌표](../maybox-board-sync/references/sources.md)를 참고한다.

| 모드 | 판정 | 시작 목표 |
| --- | --- | --- |
| 자율 실행 | 기대 결과가 명확하고 남은 선택을 기존 합의·코드로 판단 가능 | 필요한 조사·계획·구현·검증을 진행해 PR·리뷰·머지까지 완료 |
| 함께 설계 후 실행 | 중요한 정책·사용자 흐름·책임·예외가 미합의 | 담당 세션에서 사용자와 설계하고, 합의 뒤 같은 세션에서 자율 실행 |

작업 크기와 사람의 판단 부담을 혼동하지 않는다. 코드로 확인할 사실은 조사로 맡긴다. 추천안이 준비된 좁은 선택 하나는 자율 실행 중 질문으로 처리할 수 있다. 중요한 설계 묶음도 독립 구현과 병행하되, 사용자와 집중 논의할 묶음은 기본 하나씩 시작한다.

설계 세션의 질문은 사용자에게 직접 한다. 조율자는 대화를 중계하거나 이미 승인된 설계를 재심사하지 않고, 진행·의존성·충돌을 추적한다. 합의 시 문제·범위와 후속 범위·주요 결정·완료 검증·남은 사람 확인을 실행 합의로 남긴다. 실제 사용자 답변으로 실행이 승인되면 같은 세션·worktree에서 계속한다. 조율자는 자기 원장·brief·결정 기록을 갱신하고, 담당 세션이 자기 상태·질문·보고 파일을 갱신하도록 전달한다. 새로운 정책을 임의로 합의에 끼워 넣지 않는다.

## 세션 배정

배정 전에 [세션·보고 계약](references/session-contract.md)을 읽고 묶음마다 brief와 상태 파일을 준비한다. 조율 원장과 실제 기존 세션·PR을 대조하여 진행 중인 작업은 이어간다. 생성·재개 요청 결과가 불명확하면 등록된 세션을 확인한 뒤 재시도한다.

- 명시적으로 요청된 새 Codex 세션은 앱의 `list_projects` → `create_thread`를 사용한다. 이 워크플로의 기본은 별도 worktree이며, 실제 사용자 요청 또는 사용자가 승인한 기본 정책 범위에서 사용한다. 그 승인이 확인되지 않으면 필요한 경계를 확인하고 생성했다고 주장하지 않는다. 선택한 저장소·기준 ref와 현재 승인 상태를 기록한다. 네이티브 세션의 모델은 사용자가 지정하지 않았다면 사용자 기본값을 유지한다.
- 새 제목은 `[실행]` 또는 `[설계]`와 이슈·결과를 담는다. 생성 준비가 끝나 실제 threadId를 얻으면 `move_thread_to_sidebar_section(sectionId="pinned")` 등 현재 pin 도구로 고정하고 실제 목록에서 확인한다. 대기 중 clientThreadId를 threadId로 사용하지 않는다. 생성된 세션은 사용자에게 링크·생성 표시로 전달한다.
- 기본 권한 의도는 Full access다. 현재 런타임의 실제 권한·설정 가능한 필드를 확인한다. `create_thread`에 권한 인자가 없으면 넣지 않고, 부모 권한을 새 세션 권한으로 단정하지 않는다. 확인 불가·부족한 권한은 상태에 남기고 필요한 조정만 안내한다. 권한 프롬프트를 보냈다는 사실은 설정 증거가 아니다.
- Claude에서도 같은 계약과 파일을 사용한다. Codex 앱 세션 도구가 없으면 실행 가능한 인계 brief를 만들고 세션 생성·pin이 미실행임을 밝힌다. 사용자가 요청하지 않은 CLI 백그라운드 세션이나 서브에이전트로 대체하지 않는다. 자격 증명을 런타임 사이에 복사하지 않는다.

각 담당 세션은 별도 worktree의 유일한 writer다. 조율자·리뷰어는 그 소스를 직접 수정하지 않는다. 공용 API·마이그레이션·기기·DB는 소유와 통합 순서를 정한다. 승인된 고유 테스트 자원을 사용하고 기존·운영·공유 DB 적용과 실제 배포는 별도 승인 범위로 둔다.

## 질문과 결정

자율 실행의 기술 선택·네이밍·테스트·범위 내 설계는 담당 세션이 판단하고 주요 이유를 기록한다. 다른 묶음과의 경계·기존 합의 해석·통합 순서는 조율자에게 질문한다. 조율자는 근거로 결정할 수 있으면 답하고, 새로운 제품 정책·운영 사실·사용자 선호이면 선택지와 추천·영향을 정리해 사용자에게 묻는다.

질문에는 기다리는 대상과 답변 후 가능한 행동을 적는다. 같은 질문을 담당 세션과 부모에서 동시에 반복하지 않는다. 설계 세션의 직접 대화, 조율자의 기술 판단, 사용자의 승인을 출처별로 구분한다. 실제 최신 사용자 답변을 확인하고 원장·담당 상태에 반영한다. heartbeat·상태 질문·무응답을 제품 승인으로 해석하지 않는다.

담당 세션의 공유 `questions.json`·`status.json`·`report.md`가 기본 전달 경로다. child→parent 메시지 기능이 없어도 조율자가 읽어 회수한다. 부모의 지시만으로 다른 채팅에 답장을 보낼 권한이 생겼다고 가정하지 않는다. 직접 메시지는 해당 방향의 실제 사용자 승인과 도구가 있을 때 보조로 사용한다.

## 진행 감시와 재개

위임 후에는 실제 진행을 기다려 확인한다. 조율자가 활성인 동안 compact `wait_threads`로 여러 세션의 cursor를 유지한다. 최종 보고·질문·상태 불일치가 생길 때 필요한 최근 대화와 파일·로그를 읽는다. 새 세션을 만들고 끝내거나 worker의 자발적 보고에만 의존하지 않는다.

| 관측 | 조율자의 행동 |
| --- | --- |
| 실제 명령 실행 중, 로그 진전 있음 | 중복 실행 없이 결과를 기다림 |
| 사용자·외부 조건 대기와 근거 일치 | 질문 위치·필요 행동 표시, 종속 작업은 유지하며 독립 작업만 진행 |
| idle인데 미완료, 실행 중 명령·질문·대기 이유 없음 | 최근 사용자 지시·산출물을 확인하고 기존 세션에 다음 구체 행동을 지시해 재개; 실제 활동 재확인 |
| active인데 상태·로그가 오래됨 | 명령·세션 오류를 조사해 장기 실행과 정체를 구분; 시간만으로 완료·실패 판정하지 않음 |
| PR 준비·완료 주장 | 실제 고정 커밋·보고·검증·PR 결과와 대조 |

재개 요청의 세션·행동·결과를 원장에 남기고 같은 요청을 중복 전송하지 않는다. 담당 세션에 접근할 수 없으면 복구를 먼저 확인한다. 대체 writer는 기존 writer가 중단됐는지와 변경 보존을 확인한 뒤 배정한다.

사용자가 계속 조율·감시하도록 요청한 장기 작업은 기존 관련 automation을 찾아 재사용하거나 앱 heartbeat를 등록한다. 기본 점검 간격은 10분이며 작업·대기 상태에 맞게 조정한다. prompt에는 원장 경로·다음 행동·승인 경계·중복 방지·종료 조건을 넣고 변화 없는 점검은 조용히 한다. 자동화가 실제 등록·활성화됐는지 확인한다. 스킬 파일만으로 미래 감시가 실행되지 않으며 앱·호스트 조건이나 미지원 런타임의 한계는 밝힌다. 실제 완료 또는 사용자 중단 시 이 작업의 모니터를 중지한다.

## 리뷰·머지·마감

구현과 검증이 준비되면 [PR·완료 계약](references/pr-and-completion.md)을 읽는다. 자기 리뷰만으로 머지하지 않고 조율자가 별도 읽기 전용 리뷰를 배정한다. worker가 수정·추가 커밋을 만들면 필요한 delta만 재리뷰하며, 이미 끝난 전체 리뷰·무관한 테스트를 반복하지 않는다.

조율자는 실제 현재 HEAD의 승인 범위·완료 근거·필수 CI·리뷰 지적·필요한 사람 결정을 확인하고 같은 저장소의 머지를 직렬화한다. 담당 세션에 정확한 PR·HEAD의 머지 차례를 부여하면 담당 세션이 머지·결과 보고까지 수행한다. 조율자가 직접 실행하는 경우도 같은 기준이다. HEAD가 바뀌면 이전 차례를 그대로 사용하지 않는다. 운영 배포나 DB 적용은 머지 완료에 포함하지 않는다.

조율자는 실제 MERGED·merge SHA·대상 브랜치를 재조회하고, 티켓 전체 완료 기준이 충족된 경우 Linear 완료 근거와 Done을 저장·재조회한다. 설계만 완료했거나 후속 필수 범위가 남으면 원 티켓을 구현 완료로 바꾸지 않는다.

## 사용자 보고

한국어로 의미 있는 시작·진전·완료·실패·필요 행동만 간결히 알린다. 상태 질문에는 다음을 한눈에 정리한다.

| 묶음·세션 | 모드·현재 단계 | 확인된 결과·다음 행동 | 사람 개입 |
| --- | --- | --- | --- |
| 이슈·세션 링크 | 설계/실행·실제 단계 | 커밋·PR·검증 근거와 남은 단계 | 정도·무엇·어느 세션에서·언제, 없으면 없음 |

완료 보고에는 결과·주요 결정·실제 PR/머지·검증·남은 범위와 사람 확인을 담는다. 새 pin은 기본이며, 완료된 세션의 unpin·archive·worktree 정리는 사용자 요청 또는 확인된 정리 정책에 따른다.

사용자가 조율자 환경을 유지하며 위임 세션·worktree를 정리하도록 요청하면 [close-delegated-work](../close-delegated-work/SKILL.md)를 적용한다. 미완료 작업과 사용자 확인용 환경은 현재 승인·보존 조건에 따라 남긴다.
