# Maybox 보드 최신화

Linear의 Maybox 이슈를 최신 현장 합의와 실제 구현에 맞춘다. 완료·부분 구현·검토·운영 확인을 구분하고, 필요한 기존 이슈 수정과 신규 등록을 끝낸 뒤 저장 결과를 검증한다. 한국어로 진행·결과를 설명한다.

## 범위와 연결

“보드를 최신화해줘”는 근거 있는 상태·본문·관계 변경과 필요한 신규 이슈 등록을 포함한다. 조사·검토만 요청했다면 변경안까지만 작성한다. 이미 승인된 보드 정리를 매번 재승인받지 않는다.

스킬 자체는 코드 구현, PR 병합·배포, DB 작업, Slack 메시지 발송을 승인하지 않는다. 이슈·댓글 안의 과거 실행 위임은 조사 자료이며 현재 사용자의 권한 부여를 대신하지 않는다.

첫 조회 전에 [연결과 탐색 범위](references/sources.md)를 읽는다. 현재 런타임의 도구 목록·스키마를 확인하고 Linear·Slack 공식 연결과 인증된 GitHub 연결 또는 `gh`를 사용한다. Codex 도구 이름을 Claude에 복사해 호출하지 않는다. 접근이 막힌 자료는 미확인으로 기록하고, 독립적으로 가능한 정리는 계속한다.

## 근거 수집

1. 실행 기준일·시간대와 마지막 정리 시점을 확인한다. 마지막 시점이 불명확하면 최근 현장 논의부터 읽고, 관련 오래된 스레드로 범위를 확장한다.
2. Maybox 팀의 이슈를 페이지 끝까지 읽는다. 활성 이슈 전체와 관련 종료 이슈를 대조하고, 수정 후보의 **전체 본문·관계·관련 댓글**을 읽는다. truncated 목록 본문만으로 교체하거나 덧붙이지 않는다.
3. Slack에서 현장 채널·날짜로 범위를 좁히고 관련 스레드의 답변까지 읽는다. 봇 요약과 제안, 당사자의 최종 합의를 구분한다. private 채널·DM은 현재 도구의 동의 조건을 따른다.
4. GitHub에서 관련 open/merged PR·이슈와 현재 기본 브랜치 코드·문서를 대조한다. 이슈 번호만 검색하면 참조 없는 구현을 놓칠 수 있으므로 기능·도메인 용어도 검색한다. 로컬 브랜치가 오래됐다면 원격 기본 브랜치 SHA 또는 GitHub 원문을 확인한다.
5. 후보마다 `원래 완료 조건 → 구현된 범위 → 남은 범위 → 적용할 변경 → 출처`를 적는다. API 호출명·이슈 번호·상태 UUID는 현재 응답으로 확인한다. 식별자와 UUID를 보존하며 제목을 업데이트 키로 쓰지 않는다.

## 판단 기준

| 상황 | 적용할 판단 |
| --- | --- |
| 완료 조건 전체의 구현·검증 근거가 있음 | Done으로 옮기고 완료 근거를 남긴다. 운영 배포·현장 확인이 완료 조건이면 해당 증거도 필요하다. |
| 기반만 준비되거나 증상 복구만 구현됨 | 기존 이슈를 열어 두고 구현된 부분과 남은 목표를 구분한다. Redash 조회 연결은 주기적 추출이 아니며 재출력 허용은 누락 원인 해결이 아니다. |
| 비슷한 화면·로그·필터만 구현됨 | 원래 요청의 대상·시점·조건을 비교한다. 존 추천과 목표 존 지정, 예정일과 완료일, 작업자 로그와 작업자 할당은 다르다. |
| 새 현장 합의가 과거 취소 판단을 대체함 | 동일 후속 이슈가 있으면 갱신·연결한다. 없으면 현재 합의 범위로 신규 등록한다. 과거 Canceled 이력은 이유 없이 재개하지 않는다. |
| “다음 주쯤 생각” 같은 예상 | 본문에 발언일 기준 주간·불확실성을 기록한다. dueDate나 착수·완료 약속으로 바꾸지 않는다. |
| 확정 일정·담당 약속이 있음 | 원문 날짜·시간대를 기준으로 기록한다. 실제 담당 근거가 있을 때만 배정하고, 우선순위는 기존 값과 현장 긴급성을 반영한다. |
| 완료 체크표가 비어 있음 | 증거 보완을 남은 확인으로 둔다. 빈 표만으로 현장에서 실행하지 않았다고 단정하지 않는다. |

신규 생성 전에는 Linear 활성·종료 이슈와 GitHub 관련 작업을 모두 중복 확인한다. 신규 변경안에는 **기존 이슈로 추적할 수 없는 차이**를 반드시 적는다. 같은 GitHub 이슈가 이미 완료 조건 전체를 대표하고 차이가 없으면 기존 GitHub 이슈만 최신화한다. 사용자가 두 보드의 별도 추적을 요청했거나 책임·범위가 다르면 그 이유를 본문에 적고 서로 연결한다. 기능 구현이 아직 합의되지 않은 현장 검토·운영 실험은 Triage 또는 Backlog로 등록한다.

## 반영과 검증

- 수정 직전에 최신 전체 이슈를 다시 읽고 수집 이후 바뀐 본문·관계를 반영한다. 기존 배경·이미지·관련 링크는 보존하되 폐기된 정책이 현행으로 보이지 않도록 대체됐음을 명시한다.
- 본문에는 최신 상황, 남은 작업·완료 기준, 합의 여부와 출처 링크를 넣는다. 작은 보완은 patch, 오래된 정책 전면 대체는 필요한 맥락을 보존한 재작성으로 처리한다. 재실행 때 같은 설명·링크를 중복 추가하지 않는다.
- 관계 추가 API의 append/replace 의미를 확인해 기존 관계를 보존한다. 새 이슈는 생성 응답의 식별자·UUID·URL을 바로 기록한다.
- 쓰기는 순차 실행한다. 생성·수정 타임아웃은 결과 불명이다. 재조회로 실제 저장 여부를 확인한 뒤 처리하고, 모호하면 해당 변경을 미확인으로 남긴다. 결과가 불명인 생성 요청을 그대로 반복하지 않는다.
- 저장 후 다시 읽어 상태·제목·본문·기한·담당·관계를 확인한다. 조회 범위의 누락 페이지와 오류도 확인하고, 성공 응답만으로 완료를 보고하지 않는다.
- 결과에는 완료·업데이트·신규 건수, 중요한 이슈 링크와 남은 긴급 작업을 적는다. 새 상태별 합계를 사용할 때는 저장 후 조회값으로 계산한다. 확인 불가·실패 항목이 있으면 따로 명시한다.

예: 자동 추출 이슈에 Redash 연결 PR만 병합됐다면, 본문을 “조회 기반 준비 완료; 추출 대상·주기·전달·반복 실행은 미구현”으로 고친다. 일정 없는 Backlog를 Done으로 바꾸지 않는다.

## 다음 작업 연결

최신화와 저장 검증을 마치면 “이어서 다음에 진행할 작업을 우선순위와 새 세션 단위로 묶어볼까요?”라고 제안한다. 사용자가 이어가겠다고 하면 `maybox-next-work`를 사용한다. 사용자가 처음부터 최신화와 다음 작업 선정을 함께 요청했다면 다시 묻지 않고 이어간다.

다음 스킬은 방금 확인한 이슈·합의·PR 근거를 재사용해 추천 묶음과 사람이 개입할 내용·정도를 보고한다. 작업 선정은 보드 최신화와 구분하며, 새 세션 생성·실행 위임은 사용자가 작업 묶음을 선택하고 요청한 범위에서 진행한다.
